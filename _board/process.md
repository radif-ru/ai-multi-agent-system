# Процесс выполнения спринтов и задач

Единый свод правил: легенды, правила работы со спринтами и задачами, шаблоны, пошаговый алгоритм от открытия спринта до его закрытия. Документ **статичен** — меняется только при смене правил процесса. Любой ИИ или человек, открывший этот файл, получает полный набор инструкций для единообразного заполнения документации проекта.

Связанные документы:

- `_board/plan.md` — индекс спринтов (только таблицы, без правил).
- `_board/sprints/<NN>-<short-name>.md` — файлы спринтов.
- `_board/maintenance.md` — журнал внеспринтовой работы (хотфиксы, правки по итогам аудита; правила — §12).
- `_docs/instructions.md` — правила разработки (git-дисциплина, стиль, тесты, документация).
- `_docs/roadmap.md` — что **планируется** делать в будущих спринтах (Planned / Backlog).
- `_docs/current-state.md` — фактическое состояние кода `app/`, баги/легаси, нюансы.
- `AGENTS.md` — поведенческие гайдлайны LLM-агента.

## 0. Шпаргалка (TL;DR)

Цикл одной задачи целиком. Остальные разделы читаются **по ссылке из шага**, а не целиком.

1. Прочитать обязательный минимум и то, что нужно по типу задачи (§7.1).
2. Взять задачу — зависимости в `Done`, в `Progress` никого (§7.2).
3. **Начать:** `python3 -m scripts.task start <NN>.<stage>.<task>` — статусы, счётчики и коммит сам (§7.3).
4. Минимальный диф под проверяемый критерий успеха; для `app/` — сначала красный тест (§7.5).
5. Фактически выполнить каждый пункт DoD задачи (§7.7); отметки `[x]` проставит шаг 9.
6. Обновить `_docs/`, если меняется поведение — до коммита кода (§8).
7. `bash .agents/skills/git-discipline/scripts/preflight.sh` — зелёный (§7.6, §7.10).
8. Атомарные коммиты `feat/fix/docs/test/refactor` (§7.8).
9. **Закрыть:** `python3 -m scripts.task done <NN>.<stage>.<task> --note "<что сделано>"` (§7.9).
10. **Не делать сам:** push, merge в `main`, удаление ветки, открытие/закрытие спринта — только пользователь (§2 п.8).

Нет активного спринта, а правка нужна — §12 (журнал `maintenance.md`), а не коммит в обход доски.

## 1. Легенды

### 1.1 Статусы задач

| Статус | Описание |
|--------|----------|
| `ToDo` | Задача готова к работе (Definition of Ready выполнен). |
| `Progress` | Задача в работе. Одновременно в `Progress` — **ровно одна** задача на всей доске. |
| `Done` | Задача завершена, Definition of Done выполнен. |
| `Blocked` | Задача заблокирована (нужны внешние действия / разрешение зависимостей). |

### 1.2 Статусы спринтов

| Статус | Описание |
|--------|----------|
| `Active` | Спринт идёт, по нему есть задачи в `Progress` и/или `ToDo`. |
| `Closed` | Все задачи спринта в `Done`, Acceptance Criteria закрыты. |
| `Cancelled` | Спринт остановлен до закрытия (фиксируется причина). |

### 1.3 Приоритеты задач

| Приоритет | Когда использовать |
|-----------|--------------------|
| `high` | Основной функционал, критичный баг, блокер других задач. |
| `medium` | Улучшения, оптимизации, техдолг. |
| `low` | Nice-to-have, косметика, документация без блокеров. |

### 1.4 Объём задач

Объём — оценка **сложности для агента**, а не времени. Время для LLM-агента не показатель: «однодневную» для человека задачу агент выполняет за минуты. Реальные ограничители — размер контекста (сколько файлов держать одновременно), число шагов/tool-call'ов, blast radius (сколько модулей затрагивает правка), неоднозначность цели и наличие проверяемого критерия успеха.

Главная роль метки — **сигнал к декомпозиции**: чем больше размер, тем выше риск не пройти задачу за один проход и тем нужнее её разбить.

| Объём | Признак (для агента) | Действие |
|:-----:|:---------------------|:---------|
| XS | 1 файл, без ветвлений; критерий успеха тривиален или уже есть | делать |
| S | 1–2 файла, локальная правка, ~1 новый тест | делать |
| M | несколько файлов одного модуля, понятный критерий успеха | делать |
| L | затрагивает >1 модуль или критерий успеха неочевиден | по возможности разбить на S/M |
| XL | размытая цель, много шагов, кросс-модульно | **обязательно разбить** на задачи поменьше |

> Не получается сформулировать проверяемый критерий успеха (тест / smoke / инспекция) — признак, что объём занижен: уточнить или разбить задачу (см. `AGENTS.md` §4 «Выполнение от цели»).

### 1.5 Типы задач

| Тип | Описание | Результат | DoD-особенности |
|-----|----------|-----------|-----------------|
| `code` | Кодовая задача — меняет `app/`, тесты, конфиг. | Рабочий код + тесты. | Обязательны тесты, `pytest -q` + `flake8` зелёные. |
| `docs` | Документационная — правит только `_docs/`, `_board/`, `README.md`, `app/skills/`, `app/prompts/`. | Обновлённый документ. | Тесты — `n/a`; обязательна синхронизация ссылок (§8.1 п.6). |
| `spike` | Исследование с результатом-документом вместо кода. Решение фиксируется в `_docs/decisions.md` и/или `_docs/roadmap.md`. | Документ с выводами и рекомендациями. | Тесты — `n/a`; обязательно: решение зафиксировано, roadmap синхронизирован. |

> Тип не указывается в шапке задачи явно — он выводится из «Затрагиваемых файлов» и «Описание». Spike-задачи помечаются в названии префиксом «Spike:» (например, «Spike: RLM-подход»). DoD spike-задачи адаптируется: вместо тестов — документ создан, решение зафиксировано, roadmap синхронизирован.

## 2. Правила работы со спринтами

1. **Один активный спринт за раз.** Новый спринт открывается только после закрытия предыдущего. Исключение — заранее согласованный параллельный «фоновый» спринт (помечается явно в индексе `_board/plan.md`).
2. **Новый спринт = новая ветка.** Каждый новый спринт открывается в отдельной ветке `feature/<NN>-<short-name>` от актуальной `main`. Имя ветки фиксируется в шапке файла спринта и в индексе спринтов. Коммиты спринта идут только в эту ветку; merge в `main` делает пользователь сам — после закрытия спринта. Исключение — спринт 00 (инфраструктурный, `main`).
3. **Каждому спринту — отдельный файл с фиксированной структурой.** При старте создаётся `_board/sprints/<NN>-<short-name>.md` (двузначный `<NN>` с leading zero) по шаблону §4.1. **Декомпозиция:** спринт → этапы → задачи. Этапы нумеруются с 1, идут по порядку выполнения. Внутри этапа задачи нумеруются с 1 и имеют локальный ID `<stage>.<task>`.
4. **Зависимости задач.** Поле «Зависит от» у задачи может ссылаться на задачи внутри этого же этапа, других этапов того же спринта или задач закрытых ранее спринтов. Нельзя зависеть от задачи **другого активного** спринта (см. п.1).
5. **История спринтов неизменна.** Закрытые спринты остаются в `_board/sprints/` без правок — только секция «История изменений спринта» дополняется датой закрытия при переводе статуса. Если в закрытом спринте есть ссылки на старую структуру или нумерацию документации — они остаются как есть (архив).
6. **Индекс обновляется синхронно.** При открытии/закрытии спринта актуализируется `_board/plan.md` § «Индекс спринтов».
7. **Источник новых спринтов** — ТЗ пользователя + кандидаты из `_docs/roadmap.md` и `_docs/current-state.md`.
8. **Решения, которые принимает только пользователь** (никогда не делать автоматически, даже после успешного `pytest -q` и закрытой DoD):
   - merge ветки `feature/<NN>-<short-name>` в `main`;
   - удаление ветки спринта (локально или на remote);
   - перевод спринта в статус `Closed` или `Cancelled`;
   - `git push` в `main` или force-push в любую ветку.
   Агент готовит изменения и коммитит в ветку спринта; пользователь сам выполняет merge / push / удаление ветки.
9. **Перед открытием нового спринта** обязательно: `git checkout main && git pull` (см. §6, шаг 1). Новая ветка создаётся только от свежей `main`.

## 3. Правила работы с задачами

1. Задачи берутся в **наиболее целесообразном порядке** (детально — §3.5); как ориентир по умолчанию — сверху вниз по файлу спринта (этап 1 → этап 2 → …). Нельзя брать новую задачу, пока её зависимости (поле «Зависит от») не в `Done`.
2. В `Progress` одновременно — **ровно одна задача на всей доске**.
3. **Нумерация задач и формат коммитов:**
   - **Локальный ID** в файле спринта — двухчастный `<stage>.<task>`. `<stage>` — номер этапа в спринте (1, 2, 3, …); `<task>` — номер задачи в этапе (1, 2, 3, …). Нумерация начинается с 1 и **не совпадает** с номером пункта в оглавлении. Примеры: `1.1`, `1.2`, `2.1`, `3.6`.
   - Sprint-id в локальном ID **не дублируется**.
   - **Коммит смены статуса** делает `python3 -m scripts.task start|done <NN>.<stage>.<task>` (§7.3, §7.9), где `<NN>` — двузначный sprint-id (совпадает с префиксом имени файла спринта). Формат сообщения — `chore(plan): начать задачу 01.2.4` / `chore(plan): закрыть задачу 03.4.7`.
4. **Новые задачи можно добавлять** в активный спринт по ходу работы (это не нарушает «историю неизменности» — запрет касается только **закрытых** спринтов). Новые задачи получают следующий свободный ID в своём этапе; номера ранее закрытых задач не переиспользуются.
   - **Дополнение спринта = синхронная актуализация документации.** При добавлении/изменении задачи одновременно обновляются: файл спринта (сводная таблица §(N+2) и «История изменений спринта» §(N+3)), индекс `_board/plan.md` (сводная таблица состояния) и любая связанная документация в `_docs/`, на которую влияет новая задача. Спринт, план и доки не должны расходиться с фактическим набором задач.
   - **Работа вне формальной задачи.** Если по ходу выполняется правка вне заведённой задачи (срочная починка, побочное необходимое изменение), она всё равно **оформляется задачей в активном спринте** (постфактум допустимо) со всей сопутствующей актуализацией по предыдущему пункту. «Безымянных» изменений в обход доски быть не должно. Если активного спринта нет — правка идёт через журнал внеспринтовой работы (§12), а не «молча в `main`».
5. **Порядок выполнения.** Задачи берутся в **наиболее целесообразном порядке** — таком, который минимизирует конфликты правок и даёт более корректный результат (например, общие документационные правки вроде `README.md`/сверки ссылок — после связанных кодовых задач). Нумерация задаёт ориентир, а не жёсткую очередь; строгий порядок «сверху вниз» не обязателен. Ограничения порядка:
   - **Зависимости.** Нельзя брать задачу, пока её зависимости (поле «Зависит от») не в `Done`.
   - **Критичный баг** — можно выполнять вне очереди; причина кратко указывается в поле «Зависит от» (например, «баг блокирует тестирование»).
   - Существенное отклонение порядка от номеров — это нормально; отражается в «Истории изменений спринта».
6. **Все коммиты спринта идут в его рабочую ветку** (`feature/<NN>-<short-name>`), указанную в шапке файла спринта. Язык сообщений — по общему правилу проекта (`_docs/instructions.md` §1).
7. **Маршрутизация находок.** Найденные по ходу баг, уязвимость, недоработка или просто нужная будущая задача, которую решено **не делать сейчас** (или которая мешает текущей задаче), не «чинятся попутно» (см. `AGENTS.md` §3), а **маршрутизируются**:
   - будущий этап / новая идея развития → `_docs/roadmap.md` (статус `Planned`/`Backlog`);
   - легаси, нюанс или баг существующего кода `app/` → `_docs/current-state.md` §2.
   Если находку решено делать **сейчас** — она оформляется новой задачей в активном спринте (см. п.4). Цель — чтобы ни одна находка не терялась и не размывала scope текущей задачи.

## 4. Шаблоны

### 4.1 Шаблон файла спринта

Структура файла `_board/sprints/<NN>-<short-name>.md` фиксирована. Обязательные секции в указанном порядке:

```markdown
# Спринт <NN>. <Название>

- **Источник:** ТЗ пользователя / `_docs/roadmap.md` § ... / `_docs/current-state.md` § ...
- **Ветка:** `feature/<NN>-<short-name>` (от `main`; см. §2, п.2).
- **Открыт:** YYYY-MM-DD
- **Закрыт:** — (или YYYY-MM-DD при закрытии)

## 1. Цель спринта

1–2 абзаца: чего достигаем и почему это важно сейчас.

## 2. Скоуп и non-goals

### В скоупе
- Явный список областей, которые трогаем.

### Вне скоупа (non-goals)
- Явный список областей, которых НЕ касаемся, чтобы ограничить scope creep.

## 3. Acceptance Criteria спринта

Крупные проверяемые результаты, которые должны быть выполнены при закрытии спринта. AC спринта отличается от DoD отдельных задач: AC перекрывает эффект всего спринта целиком.

- [ ] Результат 1.
- [ ] Результат 2.
- [ ] Все задачи спринта — `Done`, сводная таблица актуальна.

## 4. Этап 1. <Название этапа>

1–3 строки о цели этапа.

### Задача 1.1. <Название задачи>

(См. §4.2 «Шаблон задачи».)

### Задача 1.2. <Название задачи>

…

## 5. Этап 2. <Название этапа>

### Задача 2.1. …

## N. Этап K. <Название>

### Задача K.1. …

## (N+1). Риски и смягчение

| # | Риск | Смягчение |
|---|------|-----------|
| 1 | …    | …         |

## (N+2). Сводная таблица задач спринта

| #   | Задача | Приоритет | Объём | Статус | Зависит от |
|-----|--------|:---------:|:-----:|:------:|:----------:|
| 1.1 | …      | …         | …     | ToDo   | —          |

> Обновляется при каждом переходе статуса и при добавлении/удалении задач.

## (N+3). История изменений спринта

- **YYYY-MM-DD** — спринт открыт, ветка `feature/<NN>-<short-name>` создана от `main`.
- **YYYY-MM-DD** — закрыта задача X.Y: <кратко>.
- **YYYY-MM-DD** — спринт закрыт (или Cancelled с причиной).
```

**Правила файла спринта:**

- Секции 1–3 (Цель, Скоуп, AC) — пишутся при открытии спринта, в идеале не меняются.
- Секции «Этапы» (4..N) — обязательно минимум один этап, у каждого — отдельная `##`-секция и минимум одна задача внутри.
- Секции (N+1)..(N+3) — обязательные вне зависимости от размера спринта.
- **Задачи внутри этапа** — оформляются по §4.2 «Шаблон задачи».
- **Порядок этапов** отражает порядок выполнения: нельзя начинать задачи этапа K, пока не закрыты все блокирующие зависимости из этапов < K.
- **Закрытие спринта:** все задачи — `Done`, все пункты AC проставлены, запись в «Истории изменений спринта» добавлена, `_board/plan.md` актуализирован (см. §10).

### 4.2 Шаблон задачи

Используется внутри файла спринта (`### Задача <stage>.<task>. <название>`):

```markdown
### Задача <stage>.<task>. <Краткое название>

- **Статус:** ToDo
- **Приоритет:** high | medium | low
- **Объём:** XS | S | M | L | XL
- **Зависит от:** Задача X.Y, Задача X.Z или —
- **Связанные документы:** `_docs/<file>.md` § <раздел>; …
- **Затрагиваемые файлы:** `app/<path>.py`, … (предполагаемые).

#### Описание

Что и зачем нужно сделать. Контекст, ссылки на источник (`_docs/current-state.md` § X.Y, либо запрос пользователя).

Конкретные шаги (если применимо):

1. Шаг 1.
2. Шаг 2.
3. …

#### Definition of Done

- [ ] Условие 1 (проверяемо: smoke / тестом / инспекцией).
- [ ] Условие 2.
- [ ] **Документация обновлена** (обязательно для задач, меняющих поведение системы): соответствующий документ в `_docs/` обновлён до коммита кода. Для чисто-документационных задач — `n/a`.
- [ ] **Тесты добавлены / обновлены** (обязательно для задач, меняющих код в `app/`): хотя бы один unit-тест на новое поведение, `pytest -q` зелёный, **порог покрытия (`--cov-fail-under`) не нарушен**. Для чисто-документационных задач (только `_docs/`, `_board/`, `README.md`, `app/skills/`, `app/prompts/`) — `n/a`.
- [ ] `git status` чист, артефакты не закоммичены.
```

> **Spike-задачи** (см. §1.5): DoD адаптируется — пункт «Тесты» → `n/a`, вместо него: «Документ-результат создан в `_docs/decisions.md` и/или `_docs/roadmap.md`, решение зафиксировано, roadmap синхронизирован».

## 5. Подготовка к сессии

Выполняется один раз на сессию работы:

1. `git status` пуст, ветка актуальна (`git pull`).
2. Активировано виртуальное окружение: `source .venv/bin/activate`.
3. Зависимости актуальны: `pip install -r requirements.txt` (если был добавлен/обновлён модуль).
4. Ollama запущена: `ollama list` отвечает; нужные модели на месте (`qwen3.5:4b`, `nomic-embed-text`, `llava:7b` или `gemma3:4b`).
5. **На активной ветке спринта** (см. `_board/plan.md` § «Индекс спринтов» → колонка «Ветка»). Если активного спринта нет — оставаться на `main` и ждать запроса пользователя на открытие нового спринта.

## 6. Открытие спринта

**Выполняется только по явному запросу пользователя.** Агент не открывает новые спринты автоматически, даже если предыдущий полностью закрыт.

0. **Предусловие.** `git status` чист; нет открытых задач со статусом `Progress` ни в одном спринте; `pytest -q` зелёный на текущей ветке.

1. **Переключиться на `main` и подтянуть свежие изменения** — обязательный шаг перед созданием новой ветки:
   ```bash
   git checkout main
   git pull --ff-only
   ```
   Если `git pull` не быстрый-вперёд (есть локальные коммиты в `main`) — остановиться, сообщить пользователю.

2. **Создать ветку** от обновлённой `main`:
   ```bash
   git checkout -b feature/<NN>-<short-name>
   ```

3. **Создать файл** `_board/sprints/<NN>-<short-name>.md` по шаблону §4.1. Заполнить секции «Цель», «Скоуп и non-goals», «Acceptance Criteria», минимум один этап с минимум одной задачей.

4. **Обновить** `_board/plan.md` — добавить спринт в таблицу «Активные» (статус `Active`, дата открытия). Если спринт раньше стоял в «Запланированные» (см. §6.1) — убрать оттуда строку.

5. **Закоммитить**:
   ```bash
   git add _board/sprints/<NN>-<short-name>.md _board/plan.md
   git commit -m "chore(plan): открыть спринт <NN> — <название>"
   ```
   > Формулировка **строго «открыть»**, не «начать» и не «создать».

> **Push, merge в `main`, удаление ветки спринта** — делает пользователь сам, по явному запросу. Агент эти действия **никогда** не выполняет автоматически (см. §2 п.8).

### 6.1 Запланированные спринты

В таблице «Запланированные» в `_board/plan.md` фигурируют **только реально созданные** файлы `_board/sprints/<NN>-<short-name>.md` со статусом `ToDo` (ветка ещё не создана). Записи про «будущие идеи без файла» в эту таблицу **не добавляются** — для них есть `_docs/roadmap.md` (см. §8.2).

**Когда создавать «запланированный» файл спринта** (без открытия ветки): если пользователь явно попросил подготовить структуру следующего спринта заранее. В остальных случаях — кандидаты на спринты живут в `_docs/roadmap.md` до момента открытия.

## 7. Выполнение задачи

Универсальный алгоритм закрытия **одной** задачи из активного спринта. Содержание задачи и её DoD берутся из `_board/sprints/<active>.md` и связанных документов в `_docs/`.

### 7.1 Прочитать документацию

Читается то, что нужно **этой** задаче: контекст не бесплатен, лишние документы вытесняют полезное и стоят токенов (`AGENTS.md` §2).

**Всегда:**

1. `AGENTS.md` — поведенческие гайдлайны (у большинства агентов уже в контексте).
2. `_board/plan.md` — какой спринт активен и какая у него ветка.
3. `_board/sprints/<active>.md` — сама задача, её DoD и зависимости.

**По условию:**

| Условие | Что прочитать |
|---------|---------------|
| Задача меняет код в `app/` | `_docs/current-state.md` §2–3 — есть ли запись про затрагиваемую область (легаси, подводные камни) |
| В задаче заполнено «Связанные документы» | Именно эти документы (`agent-loop.md` для Executor, `memory.md` для `sqlite-vec`, `tools.md` для нового tool, …) |
| Не знаешь, где лежит нужный документ | `_docs/README.md` — навигация |
| Сомневаешься в правиле (стиль, async, ошибки, тесты, секреты) | Нужный раздел `_docs/instructions.md`, а не документ целиком |
| Тема совпадает со скиллом-дисциплиной | `.agents/skills/<name>/SKILL.md` (порядок загрузки — `AGENTS.md` § «Рекомендуемый порядок загрузки») |

При расхождении документа и кода — приоритет у кода, документ обновляется после задачи отдельным `docs(...)`-коммитом.

### 7.2 Выбрать задачу

1. Открыть `_board/plan.md` → найти активный спринт → открыть его файл `_board/sprints/<NN>-<short-name>.md`.
2. Найти **первую сверху** задачу со статусом `ToDo` (сначала задачи этапа 1, затем этапа 2, …).
3. Проверить поле «Зависит от»: все указанные задачи должны быть `Done`. Если нет — взять задачу без невыполненных зависимостей.
4. Если требуются внешние действия (ТЗ, доступы, решения от пользователя), которых нет, — пометить задачу `Blocked` с причиной, остановиться.

### 7.3 Начать задачу (`Progress`)

```bash
python3 -m scripts.task start <NN>.<stage>.<task>   # пример: 03.4.7
```

Скрипт сам меняет `**Статус:** ToDo` → `Progress` в заголовке задачи и в «Сводной таблице задач спринта», пересчитывает счётчики `ToDo / Progress / Done` в `_board/plan.md`, прогоняет `check_sprint_sync` и коммитит оба файла как `chore(plan): начать задачу <NN>.<stage>.<task>`. Неожиданный текущий статус или рассинхрон доски — ошибка без коммита. Флаг `--no-commit` оставляет только правки файлов.

> В статусе `Progress` — **ровно одна задача на всей доске**.
> Править эти четыре места руками не нужно: механика детерминирована и автоматизирована (`AGENTS.md` §5).

### 7.4 Подготовить контекст

1. Прочитать «Описание» и «Definition of Done» задачи целиком.
2. Открыть в редакторе файлы из секции «Затрагиваемые файлы» (или предполагаемые по описанию).
3. Если задача связана с конкретной подсистемой — открыть параллельно соответствующий документ из `_docs/`:
   - конфиг / логирование → `stack.md` §9 + `architecture.md` §3.2–3.3;
   - LLM-клиент → `architecture.md` §3.4;
   - агентный цикл → `agent-loop.md`;
   - tools → `tools.md`;
   - память → `memory.md`;
   - skills / prompts → `skills.md` / `prompts.md`;
   - команды бота → `commands.md`.
4. Сформулировать (для себя или для LLM-помощника) короткий план шагов.

### 7.5 Реализовать

Следуем правилам `_docs/instructions.md` (минимализм, хирургические правки, цель → проверка):

1. **Самый минимальный диф**, решающий проблему.
2. **Не править соседний код** без явной задачи на это.
3. **Не добавлять «гибкости на будущее»** — реализуй ровно то, что нужно.
4. **Соблюдай существующий стиль** (импорты, нейминг, структура файлов).
5. Если встретился несвязанный баг или мёртвый код — записать в `_docs/current-state.md` §2, **не править** в этой задаче.

Цикл «правка → проверка»:

1. Внести правку.
2. Прогнать smoke-проверки (см. §7.6.1).
3. Если что-то поломалось — откатить и переделать.
4. **Для задач, меняющих код в `app/` — обязательно добавить или обновить тесты на новое поведение до зелёного состояния** (см. §7.6). Чисто-документационные задачи от этого правила освобождены — в DoD ставится `n/a`.

### 7.6 Проверка изменений

По умолчанию — **одна команда**, из корня репозитория:

```bash
bash .agents/skills/git-discipline/scripts/preflight.sh
```

В неё входят артефакты, `flake8`, `pytest` и все скрипты-гейты из §7.10 — зелёный `preflight.sh` означает, что все детерминированные проверки пройдены и задача готова к переходу в `Done`. Отдельные команды из §7.10 запускаются, только если нужна быстрая точечная проверка по ходу работы.

Конфигурация линтера — в корневом `.flake8` (`max-line-length = 120`, исключения `E203`, `W503`). Нарушения **в изменённых тобой файлах** — починить до коммита; в нетронутых — техдолг, маршрутизируется по §3 п.7.

#### 7.6.1 Smoke-тесты

Минимальный smoke-test (всегда, для задач, меняющих код в `app/`):

```bash
# 1) Импорт пакета не сломан
python -c "import app; print('OK')"

# 2) Сборка приложения (точка входа) — если затронуты handlers / main / services
python -c "import asyncio; from app.main import main; print(main)"

# 3) Один сценарий вручную (для задач, меняющих UX) — в реальном Telegram:
python -m app
# отправить /start и одну задачу, затем Ctrl+C
```

Целевые проверки (когда применимо):

- **Конфигурация** — `python -c "from app.config import Settings; print(Settings().ollama_default_model)"`.
- **LLM-клиент** изменён — `pytest tests/services/test_llm_client.py -q`.
- **Агентный цикл** изменён — `pytest tests/agents -q`.
- **Tool** изменён — `pytest tests/tools/test_<name>.py -q`.
- **`SemanticMemory` / `Archiver`** изменены — `pytest tests/services/test_memory.py tests/services/test_archiver.py -q` + ручная проверка `/new` в Telegram.
- **Handlers** изменены — `pytest tests/adapters/telegram -q` + ручная проверка соответствующей команды.
- **Middleware / Errors** — намеренно падающий хендлер локально → бот должен ответить «Что-то пошло не так», polling не падает.

Полный прогон тестов:

```bash
pytest -q                                      # все тесты
pytest tests/<затронутый-модуль> -q -v         # детально по подсистеме
pytest --cov=app --cov-report=term-missing     # покрытие (если установлен pytest-cov)
```

### 7.10 Автоматизация проверок

**Принцип:** детерминированные и повторяемые проверки — скриптом, не LLM и не глазами (см. `AGENTS.md` §5 и скилл `automation-discipline`). Если проверка выразима скриптом — запусти скрипт, не дублируй LLM-инспекцией. Зелёный скрипт — источник истины; красный — чини, а не маскируй.

**Скрипты-гейты проекта** (запуск из корня репозитория):

| Скрипт | Что проверяет | Когда запускать |
|--------|---------------|-----------------|
| `python3 -m scripts.task start\|done <NN>.<stage>.<task>` | Не проверка, а сам переход статуса: заголовок задачи, чекбоксы DoD, сводная таблица, история спринта, счётчики `plan.md` и коммит. Внутри прогоняет `check_sprint_sync`. | На старте (§7.3) и закрытии (§7.9) каждой задачи. |
| `python3 scripts/check_sprint_sync.py` | Статусы задач в файле спринта ↔ счётчики в `plan.md`; согласованность индекса спринтов и сводной таблицы (§9 п.4); отмеченные чекбоксы DoD у задач `Done` активного спринта (§7.9). | При закрытии спринта и после ручных правок доски. |
| `python3 scripts/check_env_sync.py` | `.env.example` и `Settings` синхронизированы. | После изменения настроек. |
| `python3 scripts/check_doc_links.py` | Внутренние ссылки в `_docs/`, `_board/`, `README.md` живые. | После правок документации. |
| `python3 .agents/skills/skill-authoring/scripts/check_agents_sync.py` | Формат скиллов/промптов и зеркала (symlink'и, упоминания в `AGENTS.md` и README). | После правок `.agents/`. |
| `git ls-files --cached --ignored --exclude-standard` | В git нет файлов, попадающих под `.gitignore` (секреты, `data/`, `*.db`, кэши, `graphify-out/`). Пустой вывод = чисто. | Входит в `preflight.sh` и в CI; отдельно — если делал `git add -f` или `git add .`. |
| `bash .agents/skills/git-discipline/scripts/preflight.sh` | Весь ритуал: артефакты + `flake8` + `pytest` + все скрипты-гейты выше. | Перед каждым кодовым коммитом задачи. |

> Скрипты-гейты включены в CI (`.github/workflows/test.yml`). Локальный прогон `preflight.sh` перед коммитом = тот же набор проверок.

### 7.7 Проверить Definition of Done

1. Открыть в файле спринта раздел «Definition of Done» выбранной задачи.
2. По каждому пункту — отметить чекбоксы `[x]` (выполнено).
3. Если хотя бы один пункт не закрыт — вернуться к §7.5.
4. **Обязательное обновление документации.** Если задача меняет поведение системы — обновить соответствующий документ в `_docs/` (см. §8). Это делается **до** коммита кода.
5. Прогнать `git status` — никаких лишних файлов (`*.log`, `.env`, `__pycache__/`, `data/*.db`).

### 7.8 Зафиксировать результат в git

**Перед каждым кодовым коммитом задачи (кроме `chore(plan): начать/закрыть задачу ...`) прогнать `pytest -q` и `flake8` (см. §7.6.1) — оба должны быть зелёными.** Если что-то падает (даже не связанное с задачей) — чинится и только потом коммит. См. `_docs/instructions.md` §8.2 и §8.3.

Коммиты — атомарные, [Conventional Commits](https://www.conventionalcommits.org/), в императиве. Язык сообщения — по общему правилу проекта (`_docs/instructions.md` §1):

```bash
pytest -q                              # обязательно: должно быть зелёным
git add <изменённые файлы>
git commit -m "feat(<scope>): <что сделано>"
# или: fix(...) / refactor(...) / docs(...) / test(...) / chore(...)
```

Типичные scope этого проекта:

- `feat(agents): добавить парсер JSON ответа модели`
- `feat(tools): реализовать calculator с безопасным AST-парсингом`
- `feat(memory): добавить SemanticMemory на sqlite-vec`
- `feat(handlers): добавить команду /new с архивированием в sqlite-vec`
- `fix(llm): обработать httpx.TimeoutException → LLMTimeout`
- `refactor(executor): вынести построение initial messages в отдельный метод`
- `docs(architecture): уточнить поток /new в §5`
- `test(tools): покрыть calculator случаем деления на ноль`
- `chore(plan): закрыть задачу 03.4.7`

### 7.9 Перевести задачу в `Done`

```bash
python3 -m scripts.task done <NN>.<stage>.<task> --note "<что сделано>"
```

Одна команда закрывает все пять пунктов ритуала и делает коммит `chore(plan): закрыть задачу <NN>.<stage>.<task>`:

- **Статус:** `Progress` → `Done` в заголовке задачи.
- **DoD:** все чекбоксы задачи `[ ]` → `[x]`.
- **Сводная таблица задач спринта:** статус задачи → `Done`.
- **История изменений спринта:** строка внизу — текущая дата + текст `--note`.
- **`_board/plan.md`:** счётчики `ToDo / Progress / Done` пересчитаны по фактическим статусам.

**Важно:** DoD должен быть фактически выполнен **до** команды (§7.7) — скрипт проставляет чекбоксы, а не проверяет работу. Счётчики `plan.md` — производные данные, руками их не правим.

## 8. Обновление документации `_docs/`

**Обязательный шаг для задач, меняющих поведение системы.** Выполняется **до** коммита кода (см. §7.7 и §7.8).

### 8.1 Общий порядок

1. Найти соответствующий документ (`commands.md`, `architecture.md`, `agent-loop.md`, `memory.md`, `tools.md`, `skills.md`, `prompts.md`, `stack.md`, `testing.md`, `security.md`, `console-adapter.md`, `events.md`, `vision-models.md`).
2. Внести правку.
3. Если изменилась структура каталога или появился новый документ — обновить `_docs/README.md` § «Навигация» и `_docs/project-structure.md`.
4. Если найден новый легаси-нюанс — добавить в `_docs/current-state.md` §2 (см. §8.2).
5. Если задача меняет состав / порядок будущих этапов — синхронно поправить `_docs/roadmap.md` (см. §8.2).
6. **Синхронизация ссылок (обязательно).** Если изменено название/номер раздела, переименован файл, удалён файл или перенесён пункт — пройти `grep -rn "<старое имя/номер>" _docs/ _board/ app/skills/ app/prompts/ README.md AGENTS.md` и обновить все живые ссылки. Закрытые спринты в `_board/sprints/` (статус `Closed`) — **не трогаем**, они архив (см. §2 п.5).
7. **Только относительные пути.** В документации запрещены абсолютные пути файловой системы (`/home/...`, `/Users/...`, `C:\...`). Все ссылки — относительно корня проекта: `_docs/...`, `_board/...`, `app/...`, `./architecture.md` и т. п. Это касается как markdown-ссылок, так и упоминаний в тексте/коде примеров.
8. Коммит `docs(<scope>): ...` — **отдельным коммитом** перед кодовым коммитом.

Чисто-документационные задачи (правят только `_docs/`, `_board/`, `README.md`, `.env.example`, `app/skills/`, `app/prompts/`) от требования кодовых тестов освобождены — в DoD ставится `n/a` напротив пункта про тесты. Для них всё равно обязательны §8 п.6 (синхронизация ссылок) и §8 п.7 (только относительные пути).

### 8.2 Правила работы с `current-state.md` и `roadmap.md`

Эти два документа имеют **разную роль** и не дублируют друг друга:

| Документ | Что фиксирует | Когда правится |
|----------|---------------|----------------|
| `_docs/current-state.md` | **Фактическое** состояние кода `app/` на сейчас: что работает (§1), известные баги/легаси (§2), архитектурные нюансы (§3), что точно не сломано (§4), история закрытий багов (§6). | На каждой задаче, меняющей поведение или вскрывшей нюанс. **Источник истины — код**; при расхождении правится документ. |
| `_docs/roadmap.md` | **Только будущее** — этапы со статусом `Planned` / `Backlog`, которые ещё не запущены ни одним спринтом. История закрытых этапов **не дублируется** — она в `_board/plan.md` (таблица «Закрытые») и в самих файлах спринтов. Активный спринт — в `_board/plan.md` (таблица «Активные»). | Когда: появилась новая планируемая задача/этап вне текущего спринта (добавляем); запланированный этап стартовал спринтом (удаляем из roadmap, переносим в `_board/plan.md`). |

**Куда писать новые планируемые задачи (вне текущего спринта).** Если задача относится к коду `app/` и описывает «что сделать дальше» — она идёт в `_docs/roadmap.md` в подходящий этап (или новый этап). Если это не задача, а нюанс/баг текущего кода — он идёт в `_docs/current-state.md` §2. На основе `roadmap.md` собираются файлы новых спринтов (см. §6 и §6.1).

**Читать перед задачей** (см. §7.1):

- `current-state.md` целиком — есть ли запись про затрагиваемую область, не наступаем ли на известный нюанс.
- `roadmap.md` — статус соответствующего этапа (если задача относится к плановому этапу).

**Обновлять по ходу задачи:**

1. **`current-state.md` §1 «Что работает»** — после добавления новой подсистемы / возможности (новый tool, handler, сервис). Запись по шаблону внутри §1.
2. **`current-state.md` §2 «Известные проблемы»** — при обнаружении бага / легаси, который **не правим** в текущей задаче. Шаблон записи — внутри §2.
3. **`current-state.md` §3 «Архитектурные нюансы»** — при появлении неочевидного контракта / ограничения, который должен знать каждый, кто трогает код.
4. **`current-state.md` §6 «История закрытий»** — при закрытии бага из §2 переносим запись сюда с датой и SHA коммита.
5. **`roadmap.md`** — при появлении нового планируемого этапа (`Planned`/`Backlog`); при старте спринта по этапу — этап **удаляется** из `roadmap.md` (история живёт в `_board/plan.md` и файле спринта, см. §9 п.5).

**Что в эти документы не пишем:**

- Процессные правила и шаблоны — они здесь, в `process.md`.
- Индекс активных/закрытых спринтов — он в `_board/plan.md`.
- Содержание задач текущего спринта — в `_board/sprints/<NN>-*.md`.
- История закрытых этапов — в `_board/plan.md` («Закрытые») и в файлах закрытых спринтов; в `roadmap.md` её **нет**.

**Этапы в `roadmap.md` не нумеруются.** Идентификатор этапа — его заголовок; порядок разделов не означает приоритет. Ссылки из других документов оформляются как `` `_docs/roadmap.md` § «Web-адаптер» ``. Причина: сквозная нумерация ломала все ссылки при каждой вставке или удалении этапа — правки становились кросс-документными, а протухшие «Этап N» не ловились ничем.

При **переименовании** заголовка этапа — синхронно правим ссылки (`grep -rn "«<старое название>»"` по `_docs/`, `_board/`, `app/skills/`, `app/prompts/`, `README.md`, `AGENTS.md`). Закрытые спринты в `_board/sprints/` не трогаем (см. §2 п.5) — они архив. Автопроверка: `python3 scripts/check_doc_links.py` — ссылки вида `` `<файл>.md` § «<Заголовок>» `` проверяются на существование заголовка в целевом файле.

## 9. Закрытие спринта

**Решение о закрытии принимает только пользователь.** Агент **никогда** не закрывает спринт автоматически, даже если все задачи в `Done` и все AC отмечены (см. §2 п.8). Агент **никогда** не делает merge ветки спринта в `main` и **никогда** не удаляет ветку спринта (ни локально, ни на remote) — это право пользователя.

Когда все задачи спринта — `Done`:

1. **Проверить и проставить Acceptance Criteria спринта (§3 файла спринта).** Это **обязательный шаг перед закрытием**: пройти по каждому пункту AC, верифицировать его (тестом / инспекцией кода / ссылкой на документ или коммит) и проставить чекбокс `[x]`. Если хоть один AC не выполнен — спринт **не закрывается**: либо открывается дополнительная задача, либо AC корректируется по согласованию с пользователем (с явной записью в «Истории изменений спринта»). Незаполненные `[ ]` к моменту перевода спринта в `Closed` — баг ритуала.
2. **Обязательно** спросить пользователя: «Все задачи спринта <NN> выполнены, AC закрыты. Закрывать спринт?» — и ждать явного ответа.
3. **Обновить файл спринта** `_board/sprints/<NN>-<short-name>.md`:
   - Поле **Закрыт:** YYYY-MM-DD.
   - Статус в `_board/plan.md` — `Closed`.
   - В «Истории изменений спринта» — строка о закрытии.
4. **Обновить** `_board/plan.md`:
   - Перенести спринт из «Активные» в «Закрытые».
   - Заполнить колонки: «Открыт», «Закрыт», «Статус».
5. **Закоммитить**:
   ```bash
   git add _board/sprints/<NN>-<short-name>.md _board/plan.md
   git commit -m "chore(plan): закрыть спринт <NN> — <название>"
   ```
6. **Если в `roadmap.md` был соответствующий Planned-этап** — удалить его оттуда (история есть в `_board/plan.md` «Закрытые» и в файле спринта). Это `docs(roadmap): ...`-коммит, отдельно.

> **Merge в `main`, push, удаление ветки спринта** — делает пользователь сам, по явному запросу. В коммит закрытия **не добавлять задачи следующих спринтов**.

## 10. Переход к следующей задаче

1. Вернуться к §7.2 — выбрать следующую задачу `ToDo`.
2. Если все задачи спринта — `Done`, а `ToDo` нет, — **спросить пользователя**, закрывать спринт или нет (см. §9). Не закрывать автоматически.
3. Открытие нового спринта — только по явному запросу пользователя (см. §6).

## 11. Чек-лист перед переходом к следующей задаче

Только то, что требует суждения. Механику (`pytest` с порогом покрытия, `flake8`, ссылки, синхронизацию доски, артефакты в git) проверяет `preflight.sh` — дублировать его глазами или ИИ не нужно (§7.10, `AGENTS.md` §5).

- [ ] **Definition of Done закрыт фактически**, а не формально (§7.7).
- [ ] **Для задач, меняющих код в `app/`** — добавлен или обновлён хотя бы один unit-тест на новое поведение (`_docs/instructions.md` §8.1). Для чисто-документационных задач — `n/a`.
- [ ] **`preflight.sh` зелёный** (§7.6).
- [ ] **Smoke-проверка UX**, если задача меняет поведение в канале (§7.6.1).
- [ ] **Документация обновлена там, где меняется поведение** (§8, `_docs/instructions.md` §8).
- [ ] **Задача закрыта скриптом** `python3 -m scripts.task done ...` (§7.9).
- [ ] Если последняя задача спринта — **проверить и проставить все пункты Acceptance Criteria спринта (§3 файла спринта)**, затем **спросить пользователя** про закрытие спринта; не закрывать самостоятельно (см. §9 и §2 п.8).

## 12. Работа вне спринта

Между спринтами и после их закрытия всегда остаётся мелкая работа: хотфикс, правка по итогам аудита, синхронизация документа с кодом. Открывать ради неё спринт — оверхед, а коммитить «молча» запрещено (§3 п.4). Для такой работы есть отдельный канал — журнал [`_board/maintenance.md`](./maintenance.md).

**Закрытые спринты для этого не используются.** Дописывать задачи или историю в закрытый спринт нельзя (§2 п.5): поле «Закрыт» и счётчики `plan.md` должны отражать фактический состав спринта, иначе ретроспектива и гейт `check_sprint_sync` теряют смысл.

### 12.1 Когда канал применим

Правка идёт вне спринта, если выполнены **все** условия:

1. **Нет активного спринта** (в `plan.md` таблица «Активные» пуста) — при активном спринте работа оформляется задачей в нём (§3 п.4).
2. **Объём ≤ S** (1–2 файла, локальная правка) **либо** правка чисто документационная (`_docs/`, `_board/`, `README.md`, `app/prompts/`, `app/skills/`, `.agents/`).
3. **Нет новой функциональности.** Новая возможность, новый tool/skill/команда, изменение контракта — только спринтом.
4. **Исключение — согласованный пакет.** Пакет правок по явному запросу пользователя (например, по итогам аудита) допустим без спринта, даже если он больше S: каждый коммит атомарен, `preflight.sh` зелёный, а в журнал добавляется **одна** запись на весь пакет.

Всё, что не проходит по этим условиям, — открывается спринтом (§6).

### 12.2 Ритуал

1. Сделать правку минимальным дифом (`_docs/instructions.md` §3, `AGENTS.md` §3).
2. Прогнать `bash .agents/skills/git-discipline/scripts/preflight.sh` — зелёный.
3. Добавить запись в `_board/maintenance.md` (формат — в самом файле) **тем же коммитом**, что и правку. Для пакета (п.4 выше) — одна запись, добавляется последним коммитом пакета.
4. Закоммитить по Conventional Commits (`docs(...)` / `fix(...)` / `chore(...)`) в `main`.

> `push` в `main` делает пользователь сам (§2 п.8) — агент только коммитит.

### 12.3 Связь со спринтами

- Записи журнала — **источник кандидатов** на задачи следующего спринта наравне с `_docs/roadmap.md` и `_docs/current-state.md` (§2 п.7).
- Если по ходу внеспринтовой правки нашлась задача крупнее S — она **не делается**, а маршрутизируется по §3 п.7 (`roadmap.md` / `current-state.md` §2).
- Журнал не заменяет `_docs/current-state.md`: там — фактическое состояние кода, здесь — хронология правок вне доски.
