# Инструкции по разработке

Документ описывает правила, которым должен следовать разработчик (и/или LLM-ассистент) при работе над проектом. Общие поведенческие гайдлайны LLM-агента (think before coding, simplicity, surgical changes, goal-driven) — `AGENTS.md` в корне. Процесс работы со спринтами и задачами (открытие, выполнение, закрытие) — `_board/process.md`.

## 1. Язык проекта

**Единое правило: по умолчанию — русский, но не строго.** Если на другом языке смысл понятнее (имена символов, термины из кода, англоязычные технические выражения, служебные коммиты вроде `chore(plan): начать задачу ...`, цитируемые буквально фрагменты кода/логов) — используется он. Смешивать языки в одном сообщении/документе допустимо.

Правило применяется ко **всему без исключения**:

- Сообщения в чате с пользователем и внутренние рассуждения (chain-of-thought, scratchpad, планы шагов).
- Сообщения коммитов (см. `_board/process.md` §7.8).
- Комментарии в коде и докстринги.
- Тексты в `_docs/`, `_board/`, `app/prompts/`, `app/skills/`, `README.md`, `.env.example`.
- **Логи** (сообщения `logger.info/warning/error/exception`, текст в лог-форматтере).
- Сообщения, которые бот отправляет пользователю (включая тексты ошибок и подсказок команд).

Технические идентификаторы (имена переменных/функций/классов/файлов, URL'ы, имена моделей, env-переменные, ключи словарей, литеральные значения протоколов) остаются латиницей — это часть кода, а не текста. Имена индустриальных терминов (LLM, RAG, polling, middleware, async, tool, skill, embedding) не переводим.

**Логи — частный случай этого правила** (подробно — §6). На русский переводится только **человекочитаемая часть** сообщения. Машиночитаемая часть остаётся латиницей:

- **имена событий** — `external.call` / `external.ok` / `external.fail`, `scheduler.run`, `orchestrator.mode`, `update`;
- **ключи `key=value`** — `status=`, `step=`, `kind=`, `reason=`, `attempt=`, `dur_ms=`, `user=`, `tool=`;
- **значения-перечисления** — `ok`, `error`, `llm_timeout`, `parse_error`.

Причина: по этим токенам грепают логи, строят фильтры в GlitchTip и пишут тесты — это контракт, а не текст. Пример правильной строки: `scheduler.run status=error task=42 reason=llm_timeout dur_ms=1200`; пример неправильной: `scheduler: ошибка task=42 причина=llm_timeout`.

Если получил инструкцию или фрагмент на другом языке — переключаться целиком не нужно: переведи смысл и продолжай по общему правилу.

## 2. Git-дисциплина

- Основная ветка — `main`, рабочие ветки — `feature/<NN>-<short-name>` (по одной на спринт).
- Коммиты — атомарные, в императиве, по [Conventional Commits](https://www.conventionalcommits.org/). Язык сообщения — по §1.
  - `feat(handlers): добавить команду /new`
  - `fix(memory): обработать недоступность sqlite-vec при старте`
  - `test(tools): покрыть calculator случаем деления на ноль`
  - `docs(architecture): уточнить поток /new в §5`
  - `chore(plan): начать задачу 01.2.3`
- **Ритуал коммитов на каждую задачу** — трёхэтапный цикл: `python3 -m scripts.task start <NN>.<stage>.<task>` → атомарные коммиты содержимого → `python3 -m scripts.task done <NN>.<stage>.<task> --note "..."`. Крайние шаги делает скрипт (статусы, DoD, сводная таблица, история, счётчики `plan.md`, коммит) — руками эти файлы не правим. Подробно — в `_board/process.md` §7 (§7.3 старт, §7.8 коммиты, §7.9 закрытие).
- **Коммиты вне спринта.** Если активного спринта нет, а правка нужна (хотфикс, синхронизация документа с кодом, итог аудита) — работа идёт через журнал `_board/maintenance.md`: запись добавляется **тем же коммитом**, что и правка. Условия и ритуал — `_board/process.md` §13. Коммитов в `main` без следа на доске быть не должно.
- `.gitignore` обязательно содержит: `.env`, `venv/`, `.venv/`, `__pycache__/`, `*.pyc`, `logs/`, `data/`, `*.db`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `.idea/`, `.vscode/`, `graphify-out/`. См. `project-structure.md` § «Что должно попасть в `.gitignore`».
- **Graphify** (опционально): `graphify hook install` ставит pre-commit хук для авто-обновления графа кода. См. `_docs/stack.md` §14.
- **Секреты никогда не коммитить.** Если токен / БД с приватными данными случайно попали — ротировать в @BotFather, удалить из истории (`git filter-repo`), удалить `.db`-файл.

## 3. Стиль кода

- Python 3.14+, type hints **обязательны** в сервис-слое и публичных функциях.
- Форматирование — `ruff format` (или `black`), длина строки 120.
- **Линтер — `flake8`** (конфиг в `.flake8` в корне проекта). Обязательно зелёный на изменённых файлах перед коммитом (см. §8.3).
- Импорты — `ruff` / `isort`-совместимо: stdlib → third-party → local.
- Имена: `snake_case` для функций/переменных, `PascalCase` для классов, `UPPER_CASE` для констант.
- Docstrings — краткие, единообразно в рамках файла; язык — по §1.
- Никаких `print` в продуктовом коде — только `logging`.

## 4. Async-дисциплина

- Любой I/O (HTTP, файлы в hot path, Telegram API, `sqlite-vec`) — только через `await`.
- Не использовать `requests`, `time.sleep`, блокирующие SDK. Только `httpx.AsyncClient`, `aiofiles` (если нужно), `ollama.AsyncClient`. Для синхронных библиотек (`sqlite3`, `ddgs`) — `asyncio.to_thread(...)`.
- Не создавать новый event loop внутри handlers / tools. Всё работает в loop'е, запущенном aiogram.
- Общие клиенты (HTTP, Ollama, SQLite-соединение) — создаются **один раз на приложение**, закрываются при shutdown.

## 5. Обработка ошибок

- Каждый handler / tool / агентный цикл либо сам ловит ожидаемые исключения (`LLMError`, `ToolError`, `asyncio.TimeoutError`), либо полагается на глобальный error handler в Dispatcher.
- Необработанных исключений быть не должно (см. NFR-3).
- Сообщения пользователю — человеческие, без stacktrace. Stacktrace — только в лог (`logger.exception(...)`).
- Иерархии исключений — в `app/services/llm.py` (`LLMError → LLMTimeout / LLMUnavailable / LLMBadResponse`) и `app/tools/errors.py` (`ToolError → ToolNotFound / ArgsValidationError`).

## 6. Логирование

- Конфиг один — `app/core/logging_config.py`.
- Каждый шаг агентного цикла логируется одной INFO-строкой (см. `agent-loop.md` §6).
- Каждый запрос к LLM — отдельной строкой (`model`, `len_in`, `len_out`, `dur_ms`, `status`).
- Каждый запуск tool — строкой из реестра (`tool=<name> dur_ms=<n> status=ok|error`).
- Ошибки — `logger.exception` или `logger.error(..., exc_info=True)`.
- Чувствительные данные (токен, сырые сообщения пользователей при `LOG_LLM_CONTEXT=false`) — никогда в логи.
- Текст лог-сообщений — по §1. **Имена событий** (`external.ok`, `scheduler.run`, `orchestrator.mode`), **ключи `key=value`** (`tool=<name>`, `dur_ms`, `status`, `step`, `kind`, `reason`) и **значения-перечисления** (`ok`, `error`, `llm_timeout`) — только латиницей: это машиночитаемый контракт (греп, фильтры GlitchTip, тесты). Переименование события/ключа = изменение контракта: синхронно правятся `_docs/observability.md`, `_docs/agent-loop.md`, `_docs/multi-agent.md` и тесты.

## 7. Секреты и конфиг

- Все секреты и настройки — из `.env` через `pydantic-settings`.
- `.env` — в `.gitignore`, в репо — `.env.example` с описанием каждого поля.
- Не хардкодить токены, URL'ы, имена моделей, пути к БД в коде. Всё через `Settings`.
- **Новый конфиг — не только в `Settings`, но и в `.env`/`.env.example`.** Любой новый настраиваемый параметр должен иметь значение по умолчанию в `Settings` **и** запись в `.env.example` с описанием, чтобы его можно было менять без правки кода. Исключение — секреты (их значение в `.env.example` оставляют пустым/плейсхолдером). Синхронизация `Settings` ↔ `.env.example` проверяется скриптом `scripts/check_env_sync.py` (в CI).

## 8. Тестирование

См. подробно `testing.md`. Минимум:

- `pytest` + `pytest-asyncio`.
- Unit-тесты для парсера JSON ответа модели (`tests/agents/test_protocol.py`).
- Unit-тесты для агентного цикла (мок LLM, мок tools).
- Unit-тесты для каждого tool (мок внешних зависимостей).
- Unit-тесты для `SemanticMemory` (с реальным `sqlite-vec` на `tmp_path`).
- Unit-тесты для handler'ов (мок `Executor` / `Archiver` / `OllamaClient`).
- `pytest` должен проходить локально одной командой без реального Telegram / Ollama / интернета.

### 8.1 Обязательное правило (тесты на новое поведение)

Новый или изменённый код в `app/` **не принимается без unit-теста на новое поведение**. Целевое покрытие из `testing.md` §5: пакет `app/` ≥ 70%, `app/services/` / `app/agents/` / `app/tools/` ≥ 85%.

Чисто-документационные задачи (правят только `_docs/`, `_board/`, `README.md`, `.env.example`, `app/skills/`, `app/prompts/`) от этого правила освобождены — в DoD таких задач явно ставится `n/a` напротив пункта про тесты.

### 8.2 Обязательное правило (зелёный pytest перед коммитом)

Перед каждым коммитом задачи прогнать `pytest -q` локально. Коммит идёт **только при зелёном результате**. Если тесты падают (даже не относящиеся к задаче) — сначала чинятся, и только потом фиксируются изменения. Это касается любых коммитов задачи, кроме `chore(plan): начать/закрыть задачу ...` (они не меняют код).

### 8.3 Обязательное правило (зелёный flake8 перед коммитом)

Перед каждым кодовым коммитом прогнать линтер:

```bash
.venv/bin/python -m flake8 app tests
```

Конфиг — в `.flake8` (`max-line-length = 120`, исключения `E203`, `W503`). Нарушения в **изменённых в текущей задаче файлах** — починить до коммита. Нарушения в нетронутых файлах — техдолг, закрываются отдельной задачей (§3; `_docs/current-state.md` §2).

### 8.4 CI (GitHub Actions)

Workflow `.github/workflows/test.yml` автоматически прогоняет `flake8 app tests` и `pytest -q` на каждый `push` в любую ветку и на `pull_request` в `main`. Job — один: Python 3.14 на `ubuntu-latest`, кеш pip по `requirements.txt`, без матрицы версий и без секретов. Тесты на CI запускаются **без** реальных Ollama/Telegram/сети — все внешние клиенты замоканы, `sqlite-vec` поднимается на `tmp_path`.

Контроль покрытия — часть CI: порог `--cov-fail-under` задан в `pyproject.toml` (`addopts`), поэтому `pytest -q` (и локально, и в CI) падает при покрытии `app/` ниже порога. Подробности и текущее значение порога — `testing.md` §2/§5.

Правило для веток спринта:

- Push в ветку `feature/<NN>-<short-name>` **должен** оставлять workflow зелёным. Красный CI — то же, что красный локальный `pytest -q`: чиним до того, как двигаться дальше.
- Если CI падает по причине, которой не было локально (флэйк, окружение, отсутствующая системная зависимость) — заводится отдельная задача в текущем спринте, а не маскируется через `pytest -k` или skip.
- Бейдж статуса висит в шапке `README.md` и ведёт на страницу actions workflow.

## 9. Документация

- Язык документации — по §1.
- Технические идентификаторы (имена модулей, функций, переменных, env, путей) — латиницей, как в коде.
- **Обязательное обновление документации.** Перед коммитом задачи, меняющей поведение системы, обновить соответствующий документ в `_docs/`. Коммит кода без обновления документации не допускается. См. `_board/process.md` §8.
- **Только относительные пути.** В любой документации (`_docs/`, `_board/`, `README.md`, `.env.example`, `app/skills/`, `app/prompts/`, `AGENTS.md`) запрещены абсолютные пути файловой системы (`/home/...`, `/Users/...`, `C:\...`). Все ссылки — относительно корня проекта (`_docs/...`, `_board/...`, `app/...`, `./architecture.md`).
- **Синхронизация ссылок.** При изменении названия/номера раздела, переименовании/удалении файла или переносе пункта — пройти `grep -rn` по всему репо и поправить все живые ссылки. Закрытые спринты (`_board/sprints/<NN>-*.md` со статусом `Closed`) — **не трогаем**, они архив (см. `_board/process.md` §2 п.5). Автопроверка: `python -m scripts.check_doc_links` (битые относительные ссылки и абсолютные пути ФС — ненулевой код, см. спринт 12, задача 8.1).
- Источник истины — код. При расхождении документ приводится в соответствие отдельным `docs(...)`-коммитом.

## 10. Процесс добавления фичи

Полный процесс работы с задачей (старт → реализация → проверка → коммит → закрытие) описан в `_board/process.md` §7. Для добавления новой функциональности порядок такой:

1. Описать поведение в соответствующем документе (`requirements.md` / `commands.md` / `agent-loop.md` / `tools.md` / `memory.md` / `skills.md`). **Обязательный шаг.**
2. При необходимости обновить `architecture.md` (новый компонент / поток).
3. Написать/обновить тест (красный). **Обязательный шаг для задач, меняющих код в `app/`.**
4. Реализовать (зелёный).
5. Отрефакторить, прогнать `flake8` (см. §8.3).
6. Обновить документацию, если реализация изменила поведение относительно плана из п.1; синхронизировать ссылки (§9).
7. Обновить `README.md`, если появилась новая команда / параметр / зависимость.
8. **Прогнать `pytest -q` и `flake8` — оба зелёные** (см. §8.2 и §8.3).
9. Коммит документации (если менялась) + коммит кода.

## 11. Что НЕЛЬЗЯ делать

- Использовать **облачные LLM** (OpenAI, Anthropic, Google и т. п.) — проект построен вокруг локальной LLM (`requirements.md` CON-2).
- Хранить **сырые сообщения** диалога в БД — нарушает CON-1. В архивную память пишутся только саммари.
- Заводить **другие БД**, кроме `sqlite-vec` — нарушает CON-3.
- Переходить на **webhook** в MVP — `requirements.md` CON-4.
- Возвращать ответ агента **вне JSON-схемы** из `agent-loop.md` §2 — это считается ошибкой.
- Коммитить `.env`, реальный токен, логи, `data/*.db`.
- Писать **синхронный I/O** в event loop'е (см. §4).
- **Удалять** ранее существовавший мёртвый код, не относящийся к задаче (см. `AGENTS.md` §3).
- **Расширять scope** задачи без явного согласования (см. `AGENTS.md` §2).
- **Вводить новые архитектурные решения и паттерны без согласования с пользователем.** Любое решение, выходящее за рамки уже принятой архитектуры (новый слой, новый сервис, новая абстракция, новый паттерн взаимодействия модулей, новая внешняя зависимость, смена структуры каталогов и т. п.) — сначала проговаривается и согласуется с пользователем, и только затем реализуется. В рамках задачи допустимы только локальные технические решения, не меняющие архитектуру проекта.

## 13. Автоматизация без ИИ

**Всё, что детерминировано и повторяемо, автоматизируется инструментом, а не ИИ и не ручной проверкой.** Принцип — `AGENTS.md` §5; дисциплина — скилл `automation-discipline`.

- Любую механическую, воспроизводимую сверку (линт, синхронизация конфига/доски, валидность ссылок, прогон тестов и покрытия) оформляем скриптом в `scripts/` и/или гейтом в CI (`.github/workflows/test.yml`), а не полагаемся на внимательность человека или ИИ.
- Если проверку приходится повторять руками или просить ИИ дважды — это сигнал написать инструмент: он детерминирован, быстр и не «забывает».
- ИИ и ручное ревью — для того, что требует суждения (архитектура, дизайн, неоднозначные правки), а не для того, что выражается кодом.
- Готовый гейт — источник истины: при зелёном гейте не дублируем его ИИ-проверкой; красный гейт чиним, а не маскируем (§8.2, §8.3).
- Новый инструмент — обычный код проекта: тесты в `tests/`, стиль по §3, запуск `python -m scripts.<name>`, документирование здесь и/или в `_board/process.md`.

Действующие гейты: `flake8 app tests`, `pytest -q` с порогом `--cov-fail-under` (§8.4), `scripts/check_env_sync.py` (`Settings` ↔ `.env.example`, §7), `scripts/check_sprint_sync.py` (`plan.md` ↔ файлы спринтов), `scripts/check_doc_links.py` (ссылки на файлы и разделы в markdown, §9). Все они запускаются одной командой — `bash .agents/skills/git-discipline/scripts/preflight.sh`.

Автоматизированы не только проверки, но и повторяемые **операции**: `python3 -m scripts.task start|done <NN>.<stage>.<task>` выполняет весь ритуал перехода статуса задачи (`_board/process.md` §7.3 и §7.9).
