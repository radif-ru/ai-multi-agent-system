# Журнал архитектурных решений (ADR)

Документ фиксирует архитектурные решения, принятые в ходе spike-исследований. Каждый раздел: контекст → варианты → решение → последствия.

---

## ADR-1. RLM-подход к сверхдлинным контекстам

**Дата:** 2026-07-09. **Spike:** задача 4.1 спринта 13.

### Контекст

Появились сценарии работы с длинным контекстом: разбор больших почтовых ящиков (десятки писем), длинные документы, логи. Текущий map-reduce `Summarizer` (`_docs/memory.md` §3.3) суммаризирует по чанкам, но не даёт агенту возможности «покопаться» в контексте интерактивно — выбрать подмножество, заглянуть в конкретный чанк, уточнить.

### Варианты

1. **Интеграция стороннего RLM-кода** — исследовательские реализации (например, `recursive-context` библиотеки). Плюс: готовый код. Минус: чужая зависимость, непредсказуемое качество, лицензионные риски, сложность интеграции с нашим агентным циклом.
2. **Собственный tool `context_explore`** поверх `Summarizer` — агент вызывает tool с операциями `peek` (заглянуть в чанк), `grep` (найти по ключевому слову), `summarize` (частичная суммаризация). Плюс: полный контроль, интеграция с существующим `Summarizer`, нет новых зависимостей. Минус: нужно разработать и протестировать.
3. **Статус-кво** — текущий map-reduce `Summarizer` + `memory_search`. Плюс: ноль усилий. Минус: не покрывает интерактивное исследование, агент не может «покопаться».

### Решение

**Вариант 2** — собственный tool `context_explore`. Это эволюционное развитие существующего `Summarizer`, не требующее внешних зависимостей и совместимое с local-first архитектурой. Tool даёт агенту операции `peek`, `grep`, `summarize` по чанкам длинного контекста — по сути, RLM-парадигму в нашем инструментальном слое.

### Последствия

- Новый tool `context_explore` добавляется в roadmap (§ «Интерактивное исследование длинного контекста»).
- `Summarizer` переиспользуется как базис — не нужно дублировать логику чанкинга.
- Tool — опасный (доступ к ФС через tmp-файлы), попадает в `_DANGEROUS_TOOLS` с allowlist.
- Пересмотр: если сторонняя библиотека станет зрелой и лицензионно чистой — можно вернуться к варианту 1.

## ADR-2. n8n как оркестратор интеграций

**Дата:** 2026-07-09. **Spike:** задача 4.2 спринта 13.

### Контекст

n8n — no-code оркестратор для cron-задач, webhook-триггеров, интеграций сторонних сервисов. Потенциальные сценарии: cron-дайджесты почты, webhook-триггеры для внешних событий, no-code интеграции (CRM, календари). Текущая архитектура: `EventBus` + tools + orchestrator внутри процесса, local-first.

### Варианты

1. **Добавить n8n** — Docker-сервис с n8n, интеграция через webhook с ботом. Плюс: no-code интерфейс, готовые ноды для 400+ сервисов, cron из коробки. Минус: Docker-сервис + БД (PostgreSQL), поверхность атаки (веб-интерфейс с auth), зависимость от внешнего проекта, конфликт с local-first принципом.
2. **APScheduler / systemd-таймеры внутри процесса** — cron внутри Python-процесса. Плюс: ноль новых зависимостей, local-first, полный контроль. Минус: нет no-code UI, нужно писать код для каждого сценария.
3. **Собственные tools + webhook-адаптер** (roadmap § «Webhook вместо polling (Telegram и MAX)») — расширение существующей архитектуры. Плюс: интеграция с агентным циклом, tools уже работают. Минус: cron нужно реализовать отдельно.

### Решение

**Вариант 3** — собственные tools + webhook-адаптер. n8n избыточен для single-user local-first системы: он дублирует `EventBus`, orchestrator и tools, добавляет Docker-зависимость и поверхность атаки. Cron-задачи решаются APScheduler (лёгкая библиотека, внутри процесса) или systemd-таймерами. Webhook-триггеры — через FastAPI-адаптер (roadmap § «Webhook вместо polling (Telegram и MAX)»).

### Последствия

- n8n не добавляется в проект. Запись в roadmap: отказ с обоснованием.
- Cron-задачи: APScheduler как кандидат в roadmap (после § «Webhook вместо polling (Telegram и MAX)»).
- Пересмотр: при переходе к многопользовательской системе или массовым no-code интеграциям — переоценить n8n как alternatives.

## ADR-3. Микросервисы vs модульный монолит

**Дата:** 2026-07-09. **Spike:** задача 4.3 спринта 13.

### Контекст

Текущая архитектура — модульный монолит: один Python-процесс на канал (Telegram, консоль), общий `core` с агентным циклом, `sqlite-vec` для состояния. Вопрос: разрезать ли на сервисы (Telegram-адаптер / core-агент / FastAPI-API как отдельные процессы с сетевым взаимодействием)?

### Варианты

1. **Микросервисы** — каждый адаптер и core как отдельный сервис, общение через HTTP/gRPC. Плюс: независимое масштабирование, изоляция, независимые деплои. Минус: сетевые хопы добавляют латентность к LLM-циклу (уже 1–10 с), сложность деплоя (docker-compose + service mesh), auth между сервисами, распределённое состояние.
2. **Модульный монолит (статус-кво)** — один процесс на канал, общий in-memory state. Плюс: ноль сетевых хопов, простота деплоя, локальное состояние. Минус: нельзя масштабировать горизонтально, один процесс = одна точка отказа.
3. **Эволюционный путь** — модульный монолит сейчас → FastAPI-адаптер → docker-compose → микросервисы при необходимости. Плюс: постепенное усложнение, решение принимается с фактами. Минус: возможный рефакторинг границ в будущем.

### Решение

**Вариант 3** — эволюционный путь. Для single-user local-first системы микросервисы избыточны: сетевые хопы ухудшают латентность LLM-цикла, деплой усложняется, а ценность (масштабирование, изоляция) не нужна одному пользователю. Текущий модульный монолит с отдельными процессами на канал — правильный баланс. FastAPI-адаптер (roadmap § «Web-адаптер») и docker-compose (§ «Docker / docker-compose») — следующие шаги эволюции.

### Последствия

- Архитектура остаётся модульным монолитом. Фиксируется в `_docs/architecture.md`.
- Эволюционный путь: FastAPI-адаптер → docker-compose → микросервисы при необходимости.
- Триггеры пересмотра: многопользовательность, горизонтальное масштабирование, независимые команды на компоненты.
- Roadmap § «Web-адаптер» и § «Docker / docker-compose» не меняются — они уже соответствуют эволюционному пути.

## ADR-4. Качество RAG: task-префиксы, метрика, чанкинг

**Дата:** 2026-07-20. **Spike:** задача 3.1 спринта 14.

### Контекст

Долгосрочная память (`SemanticMemory` на `sqlite-vec`) работает, но качество поиска (RAG) не аудировалось. Фактический пайплайн (`app/services/archiver.py`, `app/services/memory.py`, `app/tools/memory_search.py`, `app/services/session_bootstrap.py`):

1. `Summarizer` → саммари сессии (короткий текст, обычно < 1500 символов).
2. `chunk_text(size=1500, overlap=150)` → практически всегда 1 чанк.
3. `OllamaClient.embed(chunk, model="nomic-embed-text")` → 768d вектор, **без task-префиксов**.
4. `SemanticMemory.insert_batch` → `memory_chunks` + `memory_vec vec0`.
5. Поиск: `embed(query)` → KNN `MATCH` с пост-фильтром по `user_id`, `ORDER BY distance`.

Найденные проблемы:

- **Нет task-префиксов `nomic-embed-text`**: модель рекомендует `search_document:` для индексации и `search_query:` для поиска. Без префиксов качество семантического поиска просажено (модель обучена с префиксами).
- **Метрика `vec0` по умолчанию — L2** (Euclidean). `nomic-embed-text` выдаёт нормализованные векторы, для которых L2 и cosine монотонно связаны (ранжирование одинаковое). Смена метрики на cosine не изменит порядок результатов, но потребует пересоздания `memory_vec` — неоправданный риск для single-user.
- **Чанкинг саммари избыточен**: при текущей длине саммари (обычно < 1500 символов) `chunk_text` выдаёт 1 чанк. Чанкинг не вредит, но и не помогает. Оставляем как есть — future-proof для более длинных саммари.
- **TTL/cleanup отсутствует**: индекс `ix_memory_created` есть, но очистки старых чанков нет. Для single-user рост архива медленный, но при длительной эксплуатации БД растёт.

### Варианты

1. **Внедрить task-префиксы, оставить L2, отложить TTL** — внедрить `search_document:` / `search_query:` (задача 3.2), метрику не трогать (L2 на нормализованных векторах ≈ cosine), TTL и миграцию метрики — в roadmap.
2. **Внедрить task-префиксы + сменить метрику на cosine** — дополнительно пересоздать `memory_vec` с `distance_metric=cosine`. Плюс: теоретически точнее. Минус: миграция существующих векторов, риск для single-user, монотонность L2/cosine на нормализованных векторах делает выигрыш нулевым.
3. **Оставить как есть** — не внедрять префиксы. Минус: качество поиска остаётся пониженным.

### Решение

**Вариант 1** — внедрить task-префиксы (задача 3.2), остаться на L2 (монотонно связан с cosine для нормализованных векторов `nomic-embed-text`), TTL-cleanup и миграцию метрики — в roadmap. Архитектура БД подтверждена: `sqlite-vec` (ADR-3, local-first).

### Последствия

- **Task-префиксы** внедряются в задаче 3.2 (конфиг `EMBEDDING_DOCUMENT_PREFIX` / `EMBEDDING_QUERY_PREFIX`, пустая строка = отключить). Старый архив несовместим по качеству поиска — для single-user приемлемо (можно начать архив заново через удаление `data/memory.db` или несколько `/new`).
- **Метрика L2** остаётся. Смена на cosine отклонена: на нормализованных векторах `nomic-embed-text` ранжирование идентично, миграция неоправданна.
- **Чанкинг** остаётся (size=1500, overlap=150) — harmless, future-proof.
- **TTL/cleanup** — в roadmap (§ «TTL/cleanup долгосрочной памяти»).
- **Архитектура БД** — `sqlite-vec` подтверждена (ADR-3). Qdrant/Chroma/pgvector отклонены: local-first, single-user, ноль новых сервисов.
