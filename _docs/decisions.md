# Журнал архитектурных решений (ADR)

Документ фиксирует архитектурные решения, принятые в ходе spike-исследований. Каждый раздел: контекст → варианты → решение → последствия.

## ADR-1. RLM-подход к сверхдлинным контекстам

**Дата:** 2026-07-09. **Spike:** задача 4.1 спринта 13.

### Контекст

Появились сценарии работы с длинным контекстом: разбор больших почтовых ящиков (десятки писем), длинные документы, логи. Текущий map-reduce `Summarizer` (`_docs/memory.md` §3.3) суммаризирует по чанкам, но не даёт агенту возможности «покопаться» в контексте интерактивно — выбрать подмножество, заглянуть в конкретный чанк, уточнить.

### Варианты

1. **Интеграция стороннего RLM-кода** — исследовательские реализации (например, `recursive-context` библиотеки). Плюс: готовый код. Минус: чужая зависимость, непредсказуемое качество, лицензионные риски, сложность интеграции с нашим агентным циклом.
2. **Собственный tool `context_explore`** поверх `Summarizer` — агент вызывает tool с операциями `peek` (заглянуть в чанк), `grep` (найти по ключевому слову), `summarize` (частичная суммаризация). Плюс: полный контроль, интеграция с существующим `Summarizer`, нет новых зависимостей. Минус: нужно разработать и протестировать.
3. **Статус-кво** — текущий map-reduce `Summarizer` + `memory_search`. Плюс: ноль усилий. Минус: не покрывает интерактивное исследование, агент не может «покопаться».

### Решение

**Вариант 2** — собственный tool `context_explore`. Это эволюционное развитие существующего `Summarizer`, не требующее внешних зависимостей и совместимое с local-first архитектурой. Tool даёт агенту операции `peek`, `grep`, `summarize` по чанкам длинного контекста — по сути, RLM-парадигму в нашем инструментальном слое.

### Последствия

- Новый tool `context_explore` добавляется в roadmap (Этап 14).
- `Summarizer` переиспользуется как базис — не нужно дублировать логику чанкинга.
- Tool — опасный (доступ к ФС через tmp-файлы), попадает в `_DANGEROUS_TOOLS` с allowlist.
- Пересмотр: если сторонняя библиотека станет зрелой и лицензионно чистой — можно вернуться к варианту 1.

## ADR-2. n8n как оркестратор интеграций

**Дата:** 2026-07-09. **Spike:** задача 4.2 спринта 13.

### Контекст

n8n — no-code оркестратор для cron-задач, webhook-триггеров, интеграций сторонних сервисов. Потенциальные сценарии: cron-дайджесты почты, webhook-триггеры для внешних событий, no-code интеграции (CRM, календари). Текущая архитектура: `EventBus` + tools + orchestrator внутри процесса, local-first.

### Варианты

1. **Добавить n8n** — Docker-сервис с n8n, интеграция через webhook с ботом. Плюс: no-code интерфейс, готовые ноды для 400+ сервисов, cron из коробки. Минус: Docker-сервис + БД (PostgreSQL), поверхность атаки (веб-интерфейс с auth), зависимость от внешнего проекта, конфликт с local-first принципом.
2. **APScheduler / systemd-таймеры внутри процесса** — cron внутри Python-процесса. Плюс: ноль новых зависимостей, local-first, полный контроль. Минус: нет no-code UI, нужно писать код для каждого сценария.
3. **Собственные tools + webhook-адаптер (Этап 6 roadmap)** — расширение существующей архитектуры. Плюс: интеграция с агентным циклом, tools уже работают. Минус: cron нужно реализовать отдельно.

### Решение

**Вариант 3** — собственные tools + webhook-адаптер. n8n избыточен для single-user local-first системы: он дублирует `EventBus`, orchestrator и tools, добавляет Docker-зависимость и поверхность атаки. Cron-задачи решаются APScheduler (лёгкая библиотека, внутри процесса) или systemd-таймерами. Webhook-триггеры — через FastAPI-адаптер (Этап 6 roadmap).

### Последствия

- n8n не добавляется в проект. Запись в roadmap: отказ с обоснованием.
- Cron-задачи: APScheduler как кандидат в roadmap (после Этапа 6).
- Пересмотр: при переходе к многопользовательской системе или массовым no-code интеграциям — переоценить n8n как alternatives.

## ADR-3. Микросервисы vs модульный монолит

**Дата:** 2026-07-09. **Spike:** задача 4.3 спринта 13.

### Контекст

Текущая архитектура — модульный монолит: один Python-процесс на канал (Telegram, консоль), общий `core` с агентным циклом, `sqlite-vec` для состояния. Вопрос: разрезать ли на сервисы (Telegram-адаптер / core-агент / FastAPI-API как отдельные процессы с сетевым взаимодействием)?

### Варианты

1. **Микросервисы** — каждый адаптер и core как отдельный сервис, общение через HTTP/gRPC. Плюс: независимое масштабирование, изоляция, независимые деплои. Минус: сетевые хопы добавляют латентность к LLM-циклу (уже 1–10 с), сложность деплоя (docker-compose + service mesh), auth между сервисами, распределённое состояние.
2. **Модульный монолит (статус-кво)** — один процесс на канал, общий in-memory state. Плюс: ноль сетевых хопов, простота деплоя, локальное состояние. Минус: нельзя масштабировать горизонтально, один процесс = одна точка отказа.
3. **Эволюционный путь** — модульный монолит сейчас → FastAPI-адаптер (Этап 6) → docker-compose (Этап 9) → микросервисы при необходимости. Плюс: постепенное усложнение, решение принимается с фактами. Минус: возможный рефакторинг границ в будущем.

### Решение

**Вариант 3** — эволюционный путь. Для single-user local-first системы микросервисы избыточны: сетевые хопы ухудшают латентность LLM-цикла, деплой усложняется, а ценность (масштабирование, изоляция) не нужна одному пользователю. Текущий модульный монолит с отдельными процессами на канал — правильный баланс. FastAPI-адаптер (Этап 6) и docker-compose (Этап 9) — следующие шаги эволюции.

### Последствия

- Архитектура остаётся модульным монолитом. Фиксируется в `_docs/architecture.md`.
- Эволюционный путь: FastAPI-адаптер → docker-compose → микросервисы при необходимости.
- Триггеры пересмотра: многопользовательность, горизонтальное масштабирование, независимые команды на компоненты.
- Roadmap Этапы 5 и 9 не меняются — они уже соответствуют эволюционному пути.
